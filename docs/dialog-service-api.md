# Dialog Service API

Микросервис диалогов, выделенный из монолитного приложения. Предоставляет REST API для управления диалогами и сообщениями.

## Технологии

- PHP 8.4
- Lumen (Laravel)
- PostgreSQL
- Docker

## Архитектура

Микросервис работает как отдельный контейнер, доступный по порту 9000. Монолит обращается к нему через HTTP-запросы, сохраняя обратную совместимость для старых клиентов.

## Сквозное логирование

Все запросы содержат заголовок `X-Request-Id`, который передаётся от клиента через монолит в микросервис. Если заголовок отсутствует, генерируется новый UUID. ID логируется в каждом сервисе, что позволяет отслеживать цепочку запросов.

## API Endpoints

### 1. Отправка сообщения

**Endpoint:** `POST /api/v1/messages`

**Заголовки:**
- `X-User-Id` (обязательный) – ID отправителя (получается из токена аутентификации монолитом)
- `X-Request-Id` (опциональный) – идентификатор запроса для сквозного логирования

**Тело запроса (JSON):**
```json
{
  "recipient_user_id": 123,
  "content": "Текст сообщения"
}
```

**Успешный ответ (201 Created):**
```json
{
  "messageId": 456,
  "dialogId": 789
}
```

**Ошибки:**
- `401 Unauthorized` – отсутствует заголовок X-User-Id
- `422 Unprocessable Entity` – ошибка валидации
- `500 Internal Server Error` – ошибка сервиса

### 2. Получение диалога с пользователем

**Endpoint:** `GET /api/v1/dialogs/{userId}`

**Заголовки:**
- `X-User-Id` (обязательный) – ID текущего пользователя
- `X-Request-Id` (опциональный)

**Параметры пути:**
- `userId` – ID собеседника

**Успешный ответ (200 OK):**
```json
[
  {
    "id": 1,
    "author_user_id": 123,
    "content": "Привет",
    "created_at": "2026-04-25T08:00:00.000Z"
  },
  ...
]
```

**Ошибки:**
- `401 Unauthorized` – отсутствует заголовок X-User-Id
- `500 Internal Server Error` – ошибка сервиса

## Обратная совместимость

Старые клиенты продолжают использовать эндпоинты монолита:

- `POST /dialog/{recipientUserId}/send`
- `GET /dialog/{userId}/list`

Монолит преобразует эти запросы в вызовы микросервиса, подставляя `X-User-Id` из аутентифицированного пользователя и передавая `X-Request-Id`.

## Запуск

### Docker Compose

Микросервис добавлен в существующий `docker-compose.yml` как сервис `dialog-service`. Для запуска:

```bash
docker-compose up -d dialog-service
```

Сервис будет доступен по адресу `http://localhost:9000` (порт проброшен на хост).

### Миграции

Таблицы диалогов уже созданы монолитом (`DialogMigration`). Микросервис использует те же таблицы, поэтому дополнительные миграции не требуются.

## Логирование

Логи записываются в стандартный вывод контейнера (stdout). Для просмотра логов:

```bash
docker logs socnet_dialog_service
```

Каждая запись включает `request_id`, что позволяет связать логи разных сервисов.

## Интеграция с монолитом

Монолит использует класс `App\Domain\Dialog\DialogServiceClient` для HTTP-вызовов микросервиса. Контроллер `DialogController` был модифицирован для использования этого клиента вместо прямых вызовов use case.

## Новые клиенты

Новые клиенты могут обращаться напрямую к API микросервиса, используя заголовок `Authorization: Bearer <token>` (если добавить аутентификацию) или через монолит (рекомендуется для единой точки входа).
