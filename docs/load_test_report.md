# Отчет о нагрузочном тестировании Redis vs PostgreSQL для сервиса чата

## Цель
Сравнить производительность двух реализаций хранения данных диалогов: PostgreSQL (текущая реализация) и Redis (новая реализация).

## Методология
- Инструмент: Apache Bench (ab)
- Количество запросов: 1000
- Уровень параллелизма: 10 одновременных запросов
- Эндпоинт: POST `/dialog/2/send` (отправка сообщения пользователю с ID 2)
- Тело запроса: `{"text":"Hello, load test message"}`
- Авторизация: Bearer токен
- Окружение: локальный Docker-стек (nginx, php-fpm, PostgreSQL, Redis)
- Конфигурация переключения реализаций через параметр `dialog_storage` в `app/Config.php`

## Сравнительный анализ

| Метрика | PostgreSQL | Redis | Изменение |
|---------|------------|-------|-----------|
| Запросов в секунду | 265.18 | 353.20 | **+33.2%** |
| Среднее время запроса (мс) | 37.71 | 28.31 | **-24.9%** |
| Максимальное время запроса (мс) | 263 | 54 | **-79.5%** |
| Стандартное отклонение времени обработки | 22.7 | 5.4 | **-76.2%** |
| 99-й перцентиль (мс) | 224 | 48 | **-78.6%** |

## Выводы
1. **Производительность Redis значительно выше**: увеличение пропускной способности на 33% и снижение времени отклика на 25%.
2. **Стабильность Redis лучше**: стандартное отклонение времени обработки уменьшилось в 4.2 раза, что указывает на более предсказуемую производительность.
3. **Максимальное время отклика сократилось с 263 мс до 54 мс** (в 4.9 раза), что критично для пользовательского опыта.
4. Несмотря на большое количество failed requests (из-за различий в длине ответа), это не влияет на корректность работы API (все операции выполнены успешно).

## Рекомендации
- Для высоконагруженных чатов рекомендуется использовать Redis как основное хранилище благодаря его высокой скорости и низкой задержке.
- PostgreSQL можно оставить как резервное хранилище для долгосрочного архивирования или аналитики.
- Реализованный механизм переключения между хранилищами позволяет гибко выбирать стратегию в зависимости от нагрузки.

## Ограничения тестирования
- Тестирование проводилось на локальной среде, что не полностью отражает поведение в production.
- Не учитывалась нагрузка на чтение (получение диалогов).
- Не проводилось тестирование при большем количестве параллельных соединений (>100).
- Redis использовался без persistence, что может повлиять на надежность.
